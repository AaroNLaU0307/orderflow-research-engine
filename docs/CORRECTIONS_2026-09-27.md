## 1. The bootstrap is a day-cluster bootstrap, not a stationary block bootstrap

Corrects: `preregistration/PREREGISTRATION.md` section 6.2 ("the concrete
implementation of the brief's 'stationary block bootstrap... to respect
overlap/serial dependence'") and Appendix B.

The method (`day_cluster_bootstrap_mean` in `src/orderflow/stats.py`) draws
the calendar days that hold at least one event of the cell iid with
replacement and pools the events on the drawn days. That is a cluster
bootstrap over event-days. A stationary block bootstrap resamples blocks of
consecutive observations with random lengths; this method has no blocks
and treats days as independent. `docs/BRIEF.md` section 4.1 asked for a
stationary block bootstrap with a mean block length of one day, so this is
a change from the brief, and Appendix B's list of exceptions to the brief
omits it. The procedure is exactly the one section 6.2 specifies
(resampling unit, pooling, two-sided p); only its label is wrong.

## 2. The horizons of a signal do not always share an identical event set

Corrects: the "identical event set" statements in the README and in
`reports/FINAL_REPORT.md` section 8 (both fixed in place).

Segment purging is decided once per event, as
`preregistration/PREREGISTRATION.md` Appendix A resolution 1 requires, so
that all five horizons of a signal share one event set (the stated
precondition for reading gate 2). The quarantine, which the
pre-registration did not anticipate, nulls a forward return per horizon
(`null_returns_overlapping_quarantine` in `src/orderflow/quarantine.py`),
so an event can keep its short-horizon returns and lose its long ones. In
`reports/event_study_btc_cells.csv` this affects one H1 event: N is 4,609
at h=1/3/6 and 4,608 at h=12/48. H2, H3 and H6 have the same N at all five
horizons. The study was not re-run with per-event quarantine: that would
drop the event from h=1/3/6 as well and change those three cells, which
needs the full dataset. The "Final sweep" in
`preregistration/DEVIATIONS.md` entry 2 did not log the quarantine as a
deviation; this per-horizon nulling is where it departs from the per-event
admission of Appendix A resolution 1.

## 4. The event-accounting table counts the out-of-sample segment too

Corrects: `reports/event_study_btc.md`, "Event accounting" table.

The report is titled in-sample, but the table's "Raw" and "Final (post
warm-up+dedup)" columns count events detected over all 48 months,
out-of-sample included (the "Final" column matches the row sums of
`reports/event_counts_by_half_year.csv`, e.g. H3 281, H6 730). The
in-sample counts behind the gates are the N column of the Cells table
(H3 62, H6 286, both below the 300-event gate). No out-of-sample return
statistic appears in this or any other committed artifact.

## 5. The seed-invariance note is not "far from the FDR boundary"

Corrects: `reports/event_study_btc.md`, "Seed invariance" section ("This is
expected at 2,000,000 reps for a result this far from the FDR boundary in
either direction").

The nearest misses are close to the boundary: H1 at 30m and 1h share the
smallest BH-adjusted q, 0.109, against q = 0.10
(`reports/event_study_btc_cells.csv`), and at the pre-registered 10,000
reps one unseeded run crossed it
([`preregistration/DEVIATIONS.md`](../preregistration/DEVIATIONS.md) entry
3). The seed-invariance result at 2,000,000 reps stands; the reason given
for expecting it does not. `runners/phase3_event_study.py` now writes the
corrected sentence.
